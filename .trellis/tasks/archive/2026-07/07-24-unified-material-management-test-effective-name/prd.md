# 统一物料管理与测试料有效名称

## Goal

把“物料主数据”和“测试料型号库”在用户体验上统一到一个物料管理入口里，让现场用户按一个“物料”的概念维护、搜索、导入和打印标签；同时保留现有底层库存模型和测试料身份模型，避免把正式料与测试料不同的唯一性规则硬塞进同一张表。

核心用户价值：

- 正式料和测试料可以在同一个物料管理页面里浏览、搜索、新增和导入。
- 测试料标签、入库、库存查询、导出里能显示真实物料名称和子类别，而不是全部显示“测试料”。
- 现有本地标签打印 Excel 表头和库存/导入模板表头尽量不变，只改变取值来源。

## Background / Confirmed Facts

- 当前工作区为 `codex/test-material-identity-governance`，基线工作区干净。
- 现有测试料主数据 `materials` 是“代码壳”：
  - `materials.product_code` 保存测试料产品代码，例如 `J-999`；
  - `materials.material_name` 固定为 `测试料`；
  - `materials.sub_category` 固定为内置 `测试料` 子类别；
  - `materials.supplier` / `materials.supplier_model` 对测试料清空。
- 现有真实测试料型号保存在 `test_material_identities`：
  - 当前唯一身份为 `category + product_code + supplier_model_key`；
  - 供应商是选填信息，不参与唯一身份；
  - 当前已支持相似型号提醒：大小写和空格近似会提示确认，精确规范化重复会阻断。
- 当前物料主数据导入是：
  - 前端物料导入页面解析模板；
  - 最多 100 行；
  - 调用 `manageMaterial.batchCreate`；
  - 当前不是库存入库的“10 行分批事务协议”。
- 旧的测试料型号导入是：
  - 单独页面；
  - 最多 100 行；
  - 调用 `manageTestMaterialIdentity.batchCreate`。
- 用户已确认当前数据库为空，不保留这条独立批量导入路径；测试料批量维护统一走物料主数据导入。
- 当前库存入库模板导入 / 批量入库是另一套协议：
  - 前端最多 100 行；
  - 拆成每批 10 行；
  - 每批使用稳定 operation id；
  - 支持部分成功、失败批次重试；
  - 本任务不得改变这套入库协议。
- 现有标签预生成和库存入库已经要求测试料选择有效测试料型号，并把原厂型号作为快照写入业务数据。
- 用户已明确：
  - 数据库当前可以按空库/低历史兼容成本处理；
  - 不希望为正式料和测试料维护两个割裂页面；
  - 不希望改变已有标签打印 Excel 表头；
  - 测试料子类别应从系统维护过的子类别下拉选择；
  - 管理子类别入口仍只对管理员 / 超级管理员可见；
  - 更倾向导出/导入表头保持现状，通过动态取值变化满足业务。

## Requirements

### R1. 统一物料管理入口

- “物料管理”用户视角统一展示正式物料和测试料型号。
- 正式料列表项显示：
  - 产品代码；
  - 物料名称；
  - 子类别；
  - 原厂型号；
  - 供应商；
  - 类型：正式物料。
- 测试料列表项显示：
  - 产品代码；
  - 标签/现场物料名称；
  - 子类别；
  - 原厂型号；
  - 供应商；
  - 类型：测试料。
- 测试料代码壳不作为用户主要维护对象展示，除非需要作为新增测试料型号时的产品代码来源。
- 搜索仍按统一搜索规范执行；测试料结果使用“有效物料名称”和“原厂型号”参与展示与匹配。

### R2. 测试料型号增加有效名称与子类别

- `test_material_identities` 增加以下业务字段：
  - `label_material_name`：测试料在标签、库存、查询和导出中的物料名称；页面统一显示为“物料名称”；
  - `subcategory_key`：系统子类别稳定 key；
  - `sub_category`：系统子类别显示名快照；
  - `supplier`：选填，沿用当前语义；
  - `supplier_model` / `supplier_model_key`：沿用当前唯一身份语义。
- 测试料身份唯一性仍为：
  - `category + product_code + supplier_model_key`
- `label_material_name` 和 `sub_category` 不参与测试料身份唯一性。
- 新增/编辑测试料时必须填写：
  - 测试料产品代码；
  - 物料名称；
  - 子类别；
  - 原厂型号。
- 供应商为选填。
- 子类别必须从系统维护的子类别下拉选择；管理员可见“管理子类别”入口，普通用户不可见。

### R3. 保留底层正式料与测试料分层模型

- 正式物料仍写入 `materials`。
- 测试料代码壳仍写入 `materials`，但只承担产品代码、类别、默认单位/规格边界等主数据壳职责。
- 测试料真实显示名称、子类别、原厂型号、供应商写入 `test_material_identities`。
- 不新增数据库集合。
- 不把多个测试料型号拆成多条普通 `materials` 记录。

### R4. 物料主数据导入支持正式料与测试料同模板维护

- 现有物料主数据导入模板表头优先保持不变。
- 单次仍最多 100 行。
- 当一行 `是否测试料 = 否`：
  - 按现有正式物料主数据逻辑创建/跳过/校验；
  - 唯一识别仍是产品代码。
- 当一行 `是否测试料 = 是`：
  - 该行不再创建一条普通正式物料；
  - 后端确保存在对应测试料代码壳；
  - 创建/更新一条测试料型号记录；
  - 唯一识别为产品代码 + 原厂型号；
  - 行里的“物料名称”作为测试料 `label_material_name`；
  - 行里的“子类别”作为测试料型号子类别；
  - 行里的“供应商”为测试料型号选填供应商；
  - 行里的“原厂型号”为测试料型号必填字段。
- 如果同一个文件里测试料行出现相同产品代码 + 规范化原厂型号：
  - 应明确标记重复，不应静默覆盖。
- 如果与库内已存在测试料型号精确重复：
  - 应返回“已存在/跳过或更新”的明确结果；实现可以按当前导入语义选择跳过或幂等更新，但必须在结果文案中可理解。
- 如果出现大小写或空格近似的相似型号：
  - 延续当前相似提醒/确认机制，不把 `A C` 与 `AC` 当作硬重复。
- 该改造不改变库存入库导入的 100 行 / 10 行分批协议。

### R5. 手工新增/编辑体验

- 统一物料管理入口应允许新增正式料和新增测试料。
- 新增正式料继续进入正式物料编辑表单。
- 新增测试料直接进入测试料型号编辑表单，不再进入“测试料型号库首页后再点新增”的二次动作。
- 测试料型号编辑页：
  - 产品代码优先使用下拉选择已有测试料代码；
  - 当没有测试料代码时，提供管理员可见的维护/新增测试料代码入口或自动引导；
  - 物料名称字段页面显示为“物料名称”，并用辅助文案说明“用于标签、入库和库存展示”；
  - 子类别使用系统维护子类别下拉；
  - 管理子类别入口遵守现有权限。
- 测试料型号库列表/编辑路由可以保留作为手工维护入口，但不再保留独立测试料批量导入页面、模板导出云函数或 `manageTestMaterialIdentity.batchCreate` 接口。

### R6. 有效显示名称与快照规则

- 业务展示使用“有效物料名称”：
- 正式料：`materials.material_name`
- 测试料：`test_material_identities.label_material_name`，页面、标签和导出中统一显示为“物料名称”
- 业务展示使用“有效子类别”：
  - 正式料：`materials.sub_category`
  - 测试料：`test_material_identities.sub_category`
- 入库、批量入库、库存模板导入、标签预生成在生成业务记录时保存快照：
  - `material_name`
  - `sub_category`
  - `subcategory_key`
  - `supplier_model`
  - `supplier_model_key`
  - `supplier`
- 历史库存、标签、日志、报表和导出优先使用业务记录快照，不因之后修改测试料型号库而 retroactively 改变历史记录。
- 标签导出、本地打印模板、库存导出模板的表头不因本任务改变；只改变取值来源。

### R7. 文档、发布和部署边界

- 不新增集合。
- 需要部署受影响云函数。
- 如果共享 helper 改动，必须运行 `npm run sync:shared` 并确保共享副本一致。
- README 或现有说明应补充正式料 / 测试料有效名称的维护口径、导入口径和部署影响。

## Acceptance Criteria

- [ ] 物料管理页面能在一个入口中看到正式物料和测试料型号，并能区分类型。
- [ ] 搜索一个测试料原厂型号或测试料有效名称时，能在物料管理里搜到对应测试料型号。
- [ ] 新增测试料从统一物料管理入口直接进入测试料型号编辑页，不再要求先进入测试料型号库中间页。
- [ ] 测试料型号编辑页必须填写物料名称、原厂型号、子类别，供应商选填；页面标签只显示“物料名称”，不显示“有效物料名称/现场标签名称”这类长名称。
- [ ] 测试料型号子类别从系统子类别下拉选择，管理员可见管理入口，普通用户不可见。
- [ ] 物料主数据导入模板保持现有表头，并可在一个文件中同时导入正式料和测试料型号。
- [ ] 不再存在独立测试料型号批量导入页面、导入模板、模板导出云函数或 `manageTestMaterialIdentity.batchCreate` 接口。
- [ ] 物料主数据导入中 `是否测试料=否` 的行仍创建/维护正式物料，唯一性按产品代码。
- [ ] 物料主数据导入中 `是否测试料=是` 的行创建/维护测试料型号，唯一性按产品代码 + 原厂型号，物料名称作为测试料有效名称。
- [ ] 测试料相似型号继续按现有专业规则提醒：大小写/空格近似提示，精确规范化重复阻断或幂等返回。
- [ ] 库存入库模板导入和扫码/手工批量入库仍保持最多 100 行、10 行分批、失败批次可重试的协议。
- [ ] 测试料入库、批量入库、库存模板导入和标签预生成写入有效名称/子类别快照。
- [ ] 标签导出和库存/报表导出表头不改变；测试料导出的“物料名称”取测试料有效名称。
- [ ] 不新增集合；新增字段仅落在既有 `test_material_identities` 或既有业务快照字段中。
- [ ] `npm test` 通过。
- [ ] `git diff --check` 通过。
- [ ] `npm run preflight:deploy` 通过。

## Out of Scope

- 不改库存核心集合结构。
- 不新增搜索服务或数据库集合。
- 不改库存入库批量协议。
- 不改正式部署仍由微信开发者工具人工执行的流程。
- 不做拼音、错别字或相似词自动纠正。
- 不改变本地标签打印 Excel 的列名/表头。
